# ViT-Hの実時間化と配布の検討

2026-09-12。調査・提案であり、実行経路や通常モデルの変更は行っていない。

## ユーザー評価と方針案

ユーザーは完成した3方式動画について、SAMの2モデルとも肘の安定性が非常に高く、最後のViT-Hは肩の安定性もよく、品質だけならViT-Hと評価した。これは今回の映像での評価であり、全状況の品質合格ではない。ViT-Hを高速化検証の本命、現在のfull出力を品質基準とする提案。正式なライブ採用は未決定。

## 実時間化の見込み

手元のViT-H fullは約0.5〜0.6秒/フレームで現状のまま実用的なライブ追従には遅い。CPU同期/起動が多いが、単独プロファイル中のGPUカーネル活動だけでも117〜128msあった。計測器負荷込みなので下限性能ではないものの、CPU待ちを減らすだけで33msに届くと見込む根拠にはならない。docs/SAM_PERFORMANCE.md。

Fast SAM 3D Bodyの著者報告は、RTX 6000 Adaで自動検出込み約6.3〜8.3fps、5090の実演約65ms。身体・手のまとめ推論、GPU切り出し、静的グラフ化、中間予測/再精緻化の削減を使う。公開手順はDINOv3中心で、今回のViT-Hで同じ品質・速度を達成した証拠ではない。MHR→SMPL高速変換は本アプリでは元から使っておらず、その倍率を流用できない。中間処理削減は出力同等ではなく別試験とする。

出典： https://arxiv.org/html/2603.15603v1 （表1、図1、3.2節）、 https://github.com/yangtiming/Fast-SAM-3D-Body 、 https://raw.githubusercontent.com/yangtiming/Fast-SAM-3D-Body/main/README.md

第三者のSAM3DBody-cppもあるが、作者の実測には手の精緻化あり約0.89秒や別条件TensorRT約170msが含まれる。「C++」「real-time」という名称だけでは本件の品質/速度保証にならない。コード候補として未採用。 https://github.com/AmmarkoV/SAM3DBody-cpp

## 推奨する順番（提案）

1. **演算内容を保つ最適化**：ViT-H重み・解像度・full・顔等・既存補正を固定。定数キャッシュ、不要同期の整理、同じ演算の統合、MHRの公開ソースに基づく実行経路を評価。生3D出力とアバターの肩/肘/掌/指を基準動画と比較する。浮動小数点の差まで自動的に同等と扱わない。
2. **コンパイル/推論エンジン**：まず部分グラフを対象にCUDA GraphやTensorRT等を検証。Windows対応・対応演算・GPU実行・数値精度・初回構築時間を確認し、失敗時のCPUフォールバックを認めない。GPU演算融合も必要になる可能性がある。精度形式を変える場合は別比較。
3. **処理削減を可逆に試す**：残る場合に中間MHR更新、二段目の精緻化、身体/手の処理順を個別に変更。後段が中間関節に依存するため、26回を単純に1回へ減らして同じになるとは言わない。肩の安定性を失う設定は採用しない。前腕/指の品質も見る。
4. **ライブ＋Unity＋OBSで評価**：推論時間の中央値/p95、入力から描画までの遅延、結果の古さ、GPUメモリ、5分以上の安定性を測る。将来フレームをまとめるバッチや溜まった入力の順次処理でFPSだけを稼がない。初期到達点として実推論15Hz級、最終30Hzを検証する案だが、保証やユーザー承認済み基準ではない。画面描画の30/60fpsと推論Hzは分ける。

現在の3フレーム平均＋隣接平均判定は推論が低頻度になると時間遅延が増える。まず既定を固定して性能を測り、必要なら時間基準フィルターを別の可逆設定として評価する。補間で見た目が滑らかでも観測の遅れが消えたとは扱わない。顔/目/口は既存の良好な系統を独立して動かす。旧身体モデルとの低頻度併用を最初の解決策にはしない。

## 配り方の案

アプリ＋別のモデルパックに分け、初回セットアップでライセンスとモデルの取得/配置を案内する。今回のViT-H重み約1.69GB＋MHR約0.70GBで約2.39GB、これ以外に実行環境が必要。小さな配布物にはならない。公式HF取得は現状gatedだが、これはライセンス上の再配布許諾と分けて考える。全ユーザーの個別HF申請を必須とする決定はしていない。モデル同梱/ホストは条項・配布物の確認後に判断し、今回は外部への配布を行わない。

TensorRTエンジンはOS/GPU/バージョン依存があるため、4090で作ったファイルを全RTXへそのまま配る設計にはしない。対応環境向けの事前構築か初回構築を選ぶ。Windows対応の最小ランタイムを同梱する方向が配布には向くが、Python開発環境を先にC++へ総移植する必要はない。対応GPU/最低VRAMは今後実測する。 https://docs.nvidia.com/deeplearning/tensorrt/latest/getting-started/support-matrix.html

VRCアバターは利用者自身の書き出し方式を維持し、無改変haolan原本をアプリに同梱する前提にしない。まず4090＋Unity＋OBSで品質と速度を成立させ、その後に対応RTX範囲を増やす。重いゲームとの同時実行を必須要件には加えない。

## 見通しの補足（ユーザー質問後）

4090で、先行例と同じ品質・処理範囲のまま5090の約65msを超えると期待できる根拠は現時点ではない。前述の最適化候補は検証対象であり、研究実装を超える達成見込みではない。通常の高速RTMW3Dも相対奥行きを返しており、その復号・投影整合・符号保護ルールの再監査も重要な選択肢。HANDOFF最新項を参照。
