## 1. 目的

追加合意（2026-09-11）：欠測保持時間後・低信頼度・幾何判定不成立・人物不在・通信停止では最後の表示姿勢を保持し、待機姿勢へ戻さない。部分欠測はその部位の親ボーンに対する姿勢を保持し、他の有効部位は動かす。全体停止時は表情を含め表示姿勢を固定する。「追従が悪い」は遅延の申告として扱う。指の姿勢取得を現在の実装対象へ追加する。

ユーザーがUnityで改変したVRChat向け3Dアバターを、その見た目をなるべく保って専用アプリへ持ち出し、Webカメラ1台でリアルタイムに動かせるようにする。

対象はUnityでのアバター改変に慣れたVRCユーザー。初期の利用シーンは、座って会話や身振りをする状態。カメラから頭、表情、上半身、腕・手の動きを推定する。

提供価値は、改変済みアバターのシェーダーや追加ボーンを活かし、変換後の手作業を減らしながら、自然で反応のよいキャプチャを実現すること。

## 3. 初期仕様での仮定

以下は作業可能な初稿にするための仮定であり、ユーザーとの最終合意や動作保証ではない。

- 初期対応OSはWindowsのデスクトップ環境。
- 1人、1台のカメラ、1体のアバターを対象とする。
- 正面付近での会話・身振りを優先する。横顔や大きな回転への限界は測定する。
- 顔から肘付近まで入り、胸の前に上げた両手が映る撮影条件を基準とする。
- カメラ映像と推論はローカルで処理する。クラウド接続を実行時の必須条件にしない。
- 初期アバターは人型で、Humanoidとして扱えるものを優先する。非人型は別途評価する。
- 通常利用でPython環境やUnity Editorの起動を要求しない。Unity Editorは変換時に使用する。

## 4. 対象外と拡張候補

### 初期対象外

- VRChatクライアントそのものの再現。
- PhysBoneの掴み・伸縮、Contacts、VRC Constraints、Playable Layers、FX、メニュー等の完全互換。
- 配布された任意の`.unitypackage`を、専用アプリ単体で直接読み込む機能。
- VRMへの一律変換を前提とする方式。
- iPhone、複数カメラ、専用センサーの必須化。
- ゼロからの基盤的な顔・手・姿勢推定モデルの学習。
- アニメーション編集・録画・書き出し機能の全面的な実装。
- タルコフ等の重いゲームとの同時実行時の性能保証・必須検証。利用意向はあるが、ユーザーの明示指示により要件から除外する。同時実行が不可能と実証されたわけではない。

### 段階的な拡張候補

- 後から追加する要件として、Discord等の通話アプリでWebカメラとして選べる出力、およびコラボ相手への映像送信を記録する。初期版の実装・合格条件には含めない。直接の仮想カメラ実装かOBS経由かを含め、具体方式は後で決める。
- 細かなジェスチャーの精度向上。指の曲がりと掌の向きの基本追跡は現在の実装対象へ繰り上げた。
- Webカメラでパーフェクトシンクに近い細かな表情。iPhoneと同等の精度保証はしない。
- 全身の動作。撮影距離と顔・指の画素数との両立を別途評価する。
- 低負荷プリセット、詳細設定、自動負荷調整。
- 衣装切替や表情プリセットなど、需要のあるギミックの限定対応。

拡張候補の順番は固定しない。まず初期追跡範囲の品質を成立させる。

## 5. 利用の流れ

1. ユーザーが既存のUnityプロジェクトで、改変済みアバターを選ぶ。
2. 変換プラグインが依存物・対応機能を確認し、問題を対象オブジェクトとともに表示する。
3. 書き出し用コピーに変換を適用する。対応可能な改変ツールのビルド時処理も反映する。
4. 見た目、表情、揺れ物を確認し、専用アプリ用ファイルを出力する。
5. 専用アプリでファイルとカメラを選び、プレビューで撮影範囲を確認する。
6. 正面の自然な表情・姿勢を基準にキャリブレーションし、追跡を開始する。
7. 追跡が外れた場合は自然な姿勢へ移行し、再検出後に滑らかに復帰する。

この流れは利用体験を示すもので、画面構成や内部形式を確定するものではない。

## 6. 変換プラグインの要件

### 6.1 原本の保持

- 原本のPrefab、シーン、マテリアル、ボーン設定を上書きせずに書き出す。
- 一時コピーと生成物の保存先を明確にする。
- 変換を失敗・中断しても、元のVRCプロジェクトを従来どおり利用できること。

### 6.2 変換対象

- メッシュ、テクスチャ、対応マテリアル、ボーン階層、スキニング、BlendShape。
- 頭、目、口、肩、腕などの駆動に必要な対応関係。
- 自然な揺れに必要なボーンと衝突形状。PhysBoneの設定を近似する場合は調整可能にする。
- VRC側のまばたき・リップシンク設定などは、自動設定に利用できるか検証する。自動抽出できない場合の手動指定を用意する。

### 6.3 互換性と確認

- 初期対応シェーダー候補はlilToon等。実アバターと対象バージョンで確認してから対応済みとする。Poiyomiその他を最初から全面対応としない。
- 元と同じシェーダーでも、照明・カメラ・描画設定によって見え方が変わることを評価する。
- Modular Avatar等のビルド時処理を持つツールは、対応対象と実行方法を検証する。単にシーンをコピーして完成形とみなさない。
- 必須データ不足は書き出し前にエラーにする。省略可能な未対応機能は、影響と対象を示す。
- 任意のユーザースクリプトをパッケージに入れれば自動で動くという仕様にはしない。
- 変換形式のバージョン、必要なアプリバージョン、対象プラットフォーム等を識別可能にする。具体的なスキーマと拡張子は未定。

## 7. 再生・キャプチャアプリの要件

### 7.1 基本操作

- 対応アバターファイルの読み込み、カメラ選択、プレビュー、追跡開始・停止、再キャリブレーション。
- カメラなし、権限・占有による取得失敗、非対応アバター、GPU初期化失敗を区別して表示する。
- GPU推論を利用できない場合に、説明なくCPU推論に切り替えない。
- 一般利用の画面に推論エンジン等の内部用語を大量に出さない。性能・追跡状態の詳細は診断表示にまとめる。

### 7.2 追跡とアバター駆動

| 部位 | 初期の期待動作 | 重要な条件 |
|---|---|---|
| 頭 | 左右・上下の向き、首の傾き | 静止時に震えず、角度や移動が過大にならない |
| 目 | まばたきと開閉 | 自然な開眼時に半目にならない。左右独立制御の品質は別途評価 |
| 口 | 開閉と開き具合 | 閉口時のノイズを抑える。母音の厳密な分類は初期必須ではない |
| 上半身 | 軽い傾き、会話中の姿勢変化 | 脚が映らないことで胴体の姿勢が破綻しない |
| 腕・手 | 手を上げる、振る、左右に動かす | 体格差を補い、肘・手首の不自然な反転を抑える |
| 指 | 左右各5本の関節の曲がりを取得・反映 | 指ごとに有効判定と2観測確認。欠測した指は最後の姿勢を保持。横開き・親指の対向動作の精度は別途改善 |

- 人の関節座標をアバターのボーンへそのまま代入せず、体格・基準姿勢・関節方向を考慮する。
- 生の推定結果、信頼度、補正後の値、最終的なアバター動作を切り分けて確認できるようにする。
- 部位ごとに追跡状態を管理する。片手の追跡失敗で顔まで停止させない。
- 顔・姿勢・手の推定結果には時刻を付け、異なる時刻の結果を無造作に混ぜない。

### 7.3 見失いと復帰

- 手が机の下、画面外、体の後ろに移動したときは、不確かな推定を無制限に反映しない。
- 短い欠測保持後も最後の姿勢で停止する。待機姿勢へ移行しない。復帰時は有効観測に追従し、瞬間移動や反転を抑える。
- 処理が間に合わない場合は古いフレームを溜め続けない。最新フレームを優先する。
- 非検出時間、保持時間、復帰時の補間などの具体値は映像で調整する。

### 7.4 描画・揺れ物

- 対応する元のシェーダー、マテリアル、追加ボーンを保持する。
- 髪・服の揺れは自然さと安定性を重視し、元のPhysBoneとの完全一致は合格条件にしない。
- 補正、アニメーション、IK、揺れ物が同じボーンを奪い合わない更新順序を検証する。
- シェーダー互換性を理由なく崩すレンダーパイプラインへの移行を避ける。

### 7.5 出力

初期版の出力範囲は、アプリ内での3D表示と、自分のOBSにアバターを映すところまで。Discord等の通話アプリでWebカメラとして選択できる出力、およびコラボ相手への映像送信は後から追加する要件とする。共通3D空間や相手側でのアバター描画は要求しない。以下の具体的なツール・方式は提案であり、採用決定ではない。

- **ローカルOBS連携**：Spout2による透過映像の共有を第一候補にする。同一PC内のGPUテクスチャ共有であり、インターネット送信機能ではない。OBS側にプラグインが必要。描画UIを含めない出力と、半透明の髪・輪郭の合成品質を確認する。
- **基本的な代替経路**：通常のゲーム／ウィンドウキャプチャと単色背景。透過が利用できない経路向けに背景色を選べる案を検討する。
- **後日追加：通話アプリ向け出力**：Discord等のカメラ選択欄からアバター映像を選べることを目指す。アプリ独自の仮想カメラかOBS経由かは未定。必要な導入手順と対象アプリでの互換性は、この追加機能に着手する際に検証する。
- **後日追加：コラボ映像送信**：アバターを描画した映像をVDO.Ninja等で送信し、相手のOBSで受ける。相手にアバターを渡さず、こちらで作った見た目を送れる。回線による圧縮・遅延が加わる。
- **遠隔での背景透過**：標準的な仮想カメラ経由でアルファが保持されると仮定しない。単色背景＋受信側クロマキーを互換性重視の案とするが、髪・半透明素材・同系色の欠けを評価する。VDO.Ninja関連ツールのVP9二重トラックによるアルファ経路も比較候補。現行の専用受信プラグインでは実験的扱いで、送信側はCPUエンコードのため4090があっても軽いとは限らない。
- **共通3D空間への対応は対象外**：相手側でアバターを描画するための動きデータ送信、アバター転送、複数体の3D配置は今回のコラボ要件に含めない。追加の要望が出た場合に改めて検討する。
- **音声**：映像だけ別経路で送る場合、通話音声とのズレや二重取り込みが起こりうる。映像と同時送信するか、通話を別にして遅延補正するかは未定。ネットワーク込みの遅延はローカル追跡遅延と別に評価する。

当面の実装・検証はローカルOBS連携までとする。遠隔送信、通話アプリ互換、遠隔透過、コラボの音声同期は初期版の合格条件に含めず、これらの未確定事項で初期開発を止めない。後日の遠隔送信では既存ツールとの接続から検証する案を残す。アプリ内の独自通信、Spout2、透過の具体方式、仮想カメラ、録画機能は未採用。

## 8. 精度・性能の評価

### 8.1 評価原則

「最高精度」は、比較した候補の中で、実用的な遅延・安定性・負荷を満たす最良のものを選ぶという意味。世界最高や未比較モデルに対する優位性を保証しない。

- 4090でアバターを実際に描画しながら評価する。推論単体の速度だけを合格根拠にしない。
- GPU推論は必須だが、軽い制御やファイル処理までGPU化する必要はない。
- 平均値だけでなく、遅延や処理時間のp95、継続実行時の変動も記録する。
- モデルの画像精度、時間方向の安定性、最終表示の自然さを別々に評価する。
- カメラ露光、撮影距離、画像内の顔・手の大きさも測定条件に含める。

### 8.2 暫定的な測定目標

以下は初回比較を可能にする提案値。ユーザー合意済みの性能保証ではなく、実測後に更新する。

| 指標 | 暫定目標 |
|---|---|
| 描画 | 1080p、60 FPSを目標。基準アバターと描画設定を固定して測る |
| 認識更新 | 顔・上半身それぞれ実効30回/秒以上を初期目安とする |
| 動作から表示までの遅延 | 中央値100 ms以下、p95 150 ms以下を初期目安とする |
| 継続実行 | 30分でクラッシュ、増え続ける遅延、継続的なメモリ増加がない |
| GPU実行 | 主要モデルが意図したGPUバックエンドで動いていることを実測で確認 |

アプリ内タイムスタンプで分かる遅延と、カメラ・ディスプレイを含む実際の動作から表示までの遅延を混同しない。後者は高速度撮影等の測定方法を別途決める。入力カメラの実効FPSによる上限も記録する。

### 8.3 共通テスト動作

| テスト | 確認内容 |
|---|---|
| 正面で10秒静止 | 頭・腕の震え、開眼・閉口の誤反応 |
| うなずき、左右向き、首かしげ | 追従、遅延、回転方向、可動域 |
| 普通の会話、口の開閉、連続まばたき | 取りこぼし、誤検出、表情の過不足 |
| 片手・両手を上げて振る | 左右の取り違え、肘の反転、手首の飛び |
| 体を軽く傾ける | 下半身が見えない状態での胴体安定性 |
| 手を重ねる、顔の前に置く | 遮蔽時の破綻、顔への影響 |
| 手を机の下や画面外へ下ろして戻す | 最後の姿勢の保持、復帰時間、瞬間移動 |
| 顔を一時的に画面外へ出して戻す | 非検出時の動作と復帰 |
| 描画負荷を増やす | 推論と描画の競合、遅延の蓄積 |

同じ録画入力でモデルと補正処理を比較し、ライブ入力でカメラ取得・遅延・使用感を確認する。ランドマークに正解がない映像では数値精度を断定せず、目視評価と誤動作件数を記録する。

記録項目：GPU、CPU、メモリ、OS、ドライバ、カメラ、解像度・実効FPS、照明、アバター、描画設定、モデルと重みの版、実行バックエンド、処理時間、遅延、VRAM/RAM、追跡失敗と復帰。実測済み項目と未検証項目はHANDOFF.mdで管理する。

### 8.4 現在の評価対象と入力上の注意

- カメラ申告値は`EES-CMS-V43BK-3`。公式で確認した近い型番`CMS-V43BK-3`は1280×720のHD撮影と150°の超広角を特徴とする。`EES-`付き型番との同一性は未確認であり、確定スペックとして扱わない。
- 同一機種の場合、広範囲が映る利点がある一方、顔・指の画素数や周辺の歪みが精度の制約となる可能性がある。撮影距離、手動ピント、露光、実効FPS、顔と手の大きさを実機で確認する。
- 4090による処理性能とカメラの入力品質を分けて評価する。画像の拡大だけで失われた細部が測定可能になるとはみなさない。買い替えは現時点の必須条件にしない。
- 最初の評価アバターは`haolan`の無改変版、シェーダーはlilToon。モデルとシェーダーの版、Prefab、表情設定、追加ツールの依存はファイル確認後に記録する。
- 専用アプリ＋OBSを評価条件とし、実際の配信または録画設定でGPU競合、表示品質、フレーム落ちを評価する。タルコフ等の重いゲームとの同時実行は合格条件に含めず、そのための負荷低減を先行させない。ローカル出力と遠隔送信の評価を分ける。

## 9. 技術候補と未確定の境界

| 役割 | 有力候補 | 採用前に確認する点 |
|---|---|---|
| 変換・描画 | Unity / C#、Built-in Render Pipeline | VRCプロジェクト、シェーダー、配布アプリ、AssetBundleの互換性 |
| キャプチャ処理 | C++ネイティブモジュール | Unityとの連携、配布、画像の転送コスト、障害の扱い |
| GPU推論 | ONNX Runtime CUDA、TensorRT | モデル演算の対応、GPU上での実行範囲、精度、速度、起動時処理 |
| モデル | 顔・姿勢・手ごとの学習済みモデル | 着席・遮蔽・表情での精度、ライセンス、入力条件、速度 |
| 追跡・補正 | 独自実装、領域追跡、適応型フィルタ | 遅延と震えの両立、再検出、部位間の時刻整合 |
| アバター駆動 | Humanoid、IK、BlendShapeマッピング | 体格差、追加ボーン、モデルごとの表情対応 |
| 揺れ物 | Spring Bone系の処理 | 近似変換、衝突、追加依存、自然さ |
| 配布アバター | AssetBundle＋設定データ | バージョン互換、依存シェーダー、実行側に必要なコード |

- MediaPipe系モデルは比較候補として残すが、SDK一式や特定プラグインの採用は前提にしない。
- WindowsでCPU推論のみのプラグインはGPU必須条件を満たさない。
- TensorRTは高速化候補。採用するだけで速度・精度が向上するとみなさない。
- 推論エンジン、モデル、重み、前後処理を別々に特定する。モデル形式の変換だけで結果が一致するとは仮定しない。
- 独自実装の中心は画像前処理、GPU推論の統合、追跡、時間方向の補正、アバター駆動。モデル自体の追加学習は弱点とデータを確認してから判断する。
- Unityの書き出し側はVRC互換を重視する。再生側のバージョンは別途評価し、古いVRC指定版をそのまま一般配布アプリに採用しない。
- 配布を想定して、コードだけでなくモデル重みや依存ランタイムの配布条件も採用時に確認する。

## 10. 開発の進め方

以下は初稿で整理した作業内容。実装開始後の合意した区切りは[実装フェーズ](IMPLEMENTATION_PHASES.md)、進行状況はHANDOFF.mdに記録する。

1. **評価条件の確定**：カメラ、PC構成、代表アバター、必要な外部出力を確認し、テスト映像・測定条件を用意する。
2. **技術比較**：GPUで動く顔・上半身推定の候補を比較する。手の詳細モデルが初期用途に必要かも評価する。
3. **最小の一連動作**：1体のアバターをコピーから書き出し、専用アプリで頭・目・口・腕を動かす。
4. **4090での品質確立**：遮蔽と復帰、キャリブレーション、揺れ物、シェーダー、遅延と継続実行を調整する。
5. **配布体験の整備**：エラー表示、対応表、依存導入、ファイル互換性、使用手順を整備する。
6. **軽量化と拡張**：品質基準を保持してモデル・頻度・機能を調整する。細かな指・表情・全身は別々に評価する。

初期版の完了判定は、対応アバターの非破壊変換、主要部位の自然な追跡、追跡失敗からの復帰、GPU推論の確認、OBSでのキャプチャ、合意した遅延・性能条件、継続実行、利用手順が揃った時点とする。
